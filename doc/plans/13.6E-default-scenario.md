# 13.6E: Standard Battlefield, area terrain and catalog parity
Status: approved
Roadmap: doc/ROADMAP.md § Sub-phase 13.6E: Default Scenario & Map Preset Standardization

## Goal
Players can pick a ready-made **Standard Battlefield**, a 48"×48" table built only from catalog pieces at their default sizes and laid out along the tournament terrain mix, in the lobby and in the editor. The palette gains the two kinds of terrain it lacks: a **Rubble Field** (difficult; models inside are in cover) and a **Hazard Pool** (dangerous). Any piece can be marked difficult or dangerous in the editor. The old off-catalog `createDefaultScenarioTerrain` layout becomes a test fixture. An automated sweep checks that meshes, collision, line of sight, cover and paths agree for every catalog piece and on the built-in map.

## Decisions (agreed)
1. **One built-in map, Empty stays default.** The owner chose: "One built-in map". The map has id `standard-battlefield`, name `Standard Battlefield`, a 48×48 board, and its objectives come from `createBalancedObjectives({ width: 48, height: 48 })` (±12, ±9). The lobby's default selection stays **Empty Battlefield**. The built-in map is code data and can't be changed in place: the editor loads it as a copy (Decision 11).
2. **Two new area pieces** (palette category `area`, shown as "Area Terrain"):
   - `rubble-field`: **Rubble Field (6"×4")**. Default scale `{ x: 6, y: 0.25, z: 4 }`. Difficult, provides cover, does not block sight, not an obstacle, not walkable.
   - `hazard-pool`: **Hazard Pool (4"×4")**. Default scale `{ x: 4, y: 0.1, z: 4 }`. Dangerous, **not** difficult, no cover, does not block sight, not an obstacle, not walkable.
   - Both have a structure with **no solids and no apertures** (`{ id, solids: [] }` in `TERRAIN_STRUCTURES`), so they never block movement or sight and never use the fallback body. The footprint is the rectangle `scale.x × scale.z`, rotated with the piece.
   - Catalog metadata gets `isArea?: boolean`, `isDifficult?: boolean` and `isDangerous?: boolean`. Both area pieces have `isArea: true`.
3. **Difficult / dangerous come from data.** Use new helpers `isDifficultPiece(piece)` / `isDangerousPiece(piece)` in `mapSchema.ts`. They follow the `isClimbable` pattern: the piece's own `isDifficult` / `isDangerous` if defined, else the catalog default, else a **legacy type list** for old saved maps (difficult: `trench`, `forest`, `mud`; dangerous: `toxic`, `hazard`, `fire`), which today are hardcoded in `traversal.ts`. The engine stops naming terrain types for these rules.
4. **Detection uses segments, not just path vertices.** A path is difficult (or dangerous) if any **segment** crosses the footprint of a difficult (or dangerous) piece, including a straight walk across a rubble field whose two ends are outside it. Only segments at the piece's level count. A segment counts when some part of it inside the footprint has `y` between the piece's base − 0.25 and its top + 0.6 (the same band `findTerrainAtPosition` uses). So a model on a 3" deck or catwalk above a rubble field is not slowed, and a model standing beside a piece doesn't count. The existing 0.15" margin stays. Pathfinder / Airborne exemptions are unchanged. The rules themselves are unchanged: difficult caps movement at 6", and dangerous rolls the hazard test as today.
5. **Area cover is for models inside.** A model is inside an area piece with `providesCover` (and at its level, Decision 4's band) as follows: in a unit of **several living models**, a model counts only when its **whole base** is inside the footprint; in a **single-model** unit (or a squad down to one living model), its **centre** inside the footprint is enough (the core rules' "mostly inside"). Owner-approved after checking the core rules. This applies whatever the line of fire is, including plunging fire (the "plunging fire ignores low cover" exception does not apply to area pieces). Area pieces **never** give the intervening low-cover bonus (the 1" behind-the-piece rule stays for crates, barricades and pipes only). Squads are unchanged: cover applies when more than half the living target models are individually in cover.
6. **Models in an area piece stay on the ground.** An area piece is not a floor: moving into, across or ending in one leaves `y` at the ground (or at the floor it sits on). Picks on it resolve to the ground point beneath. Ending a move inside one is legal (it is not an end-overlap).
7. **Editor toggles.** The piece inspector gets two checkboxes for every piece, **Difficult (6" move cap)** and **Dangerous (hazard test)**, which write `piece.isDifficult` / `piece.isDangerous` (an explicit `false` overrides a catalog `true`). They show the effective value from the helpers. On placement, `placePieceAt` copies `isDifficult` / `isDangerous` from the catalog metadata (only when defined).
8. **No terrain-mix validation.** The owner chose "No": `validateMapDefinition` is not changed. The mix numbers in Decision 10 are only test targets for the built-in map.
9. **Standard Battlefield layout.** Point-symmetric about the board centre, so both sides get the same table: every piece at `(x, z, yaw)` has a twin at `(−x, −z, yaw + π)`. The catwalk is its own twin. All pieces use their catalog default scale and flags (except where the table says otherwise). Positions are on a 0.25" grid, and yaws are multiples of π/2. Starting layout (piece A; add its twin):

   The tests in PR 4 are authoritative. If one fails, the implementer may move a pair by up to 2" (keeping symmetry and the grid) and must list every change in the PR description. Bigger changes go back to Opus.
10. **Layout invariants (PR 4 tests).** Counted over pieces **excluding ladders and stairs** (access fittings):
    - at least half block sight; at least a third give cover; at least a third are difficult (12 of 33 with six rubble pairs; the beginner's guide sets a third as a minimum); at least 2 are dangerous;
    - footprint area at least 18% of the table (the tournament's "about a quarter" assumes 6–12" ruins; our biggest pieces are 6");
    - every piece inside the board; any two **obstacle** footprints at least 1.5" apart, except fittings joined on purpose (platform↔catwalk, platform↔its ladder/stairs);
    - every objective on the ground, outside both deployment zones, not inside any piece's footprint, and at least 1.5" from every obstacle footprint;
    - point symmetry (Decision 9).
11. **Lobby and editor.**
    - Lobby map select: a **Built-in maps** group with `Standard Battlefield (48"×48")`, value `builtin:standard-battlefield`. The selection sends that map as `customMap`, like a saved map. The display name is `Standard Battlefield`.
    - Editor Load list: a **Built-in** optgroup with the same entry. Loading it calls `setMap` on a deep copy with a new id (`custom-<timestamp>`) and the name `Standard Battlefield (copy)`, so saving never claims the built-in id.
12. **Legacy fixture.** `createDefaultScenarioTerrain` is removed from `shared/src` (it is only used by tests). Its layout moves **verbatim** to `shared/tests/fixtures/legacyScenarioTerrain.ts` as `legacyScenarioTerrain()`, and the client tests that used it import it by relative path, the same way they already read `shared/tests/fixtures/*.json`. Their assertions must not change. The legacy `toxic` piece in it keeps working through the legacy type list (Decision 3).

## Out of scope
- Visual dressing deferred from 13.6D (chamfers, hazard stripes, round pipes).
- More built-in maps, map thumbnails, and changes to `validateMapDefinition`.
- Making ruins or other existing catalog pieces difficult by default.
- Bigger catalog pieces to reach a 25% coverage table.

## PR 1: Area terrain in the engine  (branch: `13.6E-area-terrain-1`)
- **Layer:** shared engine
- **Files:** `shared/src/data/mapSchema.ts`, `shared/src/data/terrainStructures.ts`, `shared/src/engine/traversal.ts`, `shared/src/engine/spatial.ts`, `shared/src/index.ts` (export the helpers), new `shared/tests/engine/areaTerrain.test.ts`, `shared/tests/data/terrainStructures.test.ts`.
- **Tests first:**
  - Catalog: both area pieces exist with the Decision 2 flags. `resolveTerrainStructure` gives them zero solids and zero apertures.
  - `isDifficultPiece` / `isDangerousPiece`: piece override beats catalog, explicit `false` beats catalog `true`, legacy types (`toxic`, `forest`, …) still count, unknown types without flags don't.
  - Difficult: a straight two-point path across a rubble field (both ends outside) is difficult. A path that passes 0.5" outside it is not. A path on a 3" catwalk deck right above it is not. A Pathfinder unit is exempt. The move cap becomes 6" for a Rush across it.
  - Dangerous: a straight path across a hazard pool needs hazard dice (single model and squad `m<i>_` cases follow the existing tagging). Crossing a rubble field doesn't. Airborne is exempt.
  - Cover: a target whose centre is inside a rubble field has cover from a shooter on the ground and from a shooter on a 3" deck (plunging). A target 0.5" **behind** a rubble field (centre outside) does **not** get cover from it. A target inside a hazard pool doesn't. Squad: 3 of 4 models fully inside means cover, 2 of 4 means none, and 3 of 4 with centres inside but bases over the edge means none; a single model with its centre inside but base over the edge has cover.
  - Activating inside: when a unit is activated, each living model standing inside a dangerous piece (centre inside, at its level) rolls the hazard test (one die, or its Tough value) before the unit's action, the same way the crossing test resolves; the dice go through the server like other hazard dice (purpose `activation_hazard`, `m<i>_` tagged for squads). A model inside a dangerous piece that also moves across dangerous terrain this activation rolls only once (activation test). Airborne still exempt. Owner-approved: the core rules test models that activate in dangerous terrain.
  - Ground: `findNavPath` across a rubble field keeps every waypoint at `y = 0`, and ending inside one isn't an end-overlap.
  - Legacy: the old `toxic` piece (copy it in) still triggers hazard dice.
- **Implementation steps:**
  1. Add `'area'` to `TerrainCategory`, add `isArea` / `isDifficult` / `isDangerous` to `TerrainTypeMetadata`, add the two catalog entries and empty structures.
  2. Add `isDifficultPiece` / `isDangerousPiece` with the legacy lists, next to `isClimbable`.
  3. Rewrite `isPathDifficult` / `isPathDangerous` to test each segment against every flagged piece's footprint at its level (Decision 4), using the helpers. Remove the hardcoded type names.
  4. Add the activation hazard test (dice requested where activation starts; resolution reuses the existing hazard wound path), with HUD log label "Hazard (activated in dangerous terrain)".
  5. In `findCoverSource`, add the area-inside check before the per-piece loop's other branches, and skip area pieces in the low-cover branch.
  6. Check `findTerrainAtPosition` callers that derive heights. Area pieces must not raise a model (add a guard if a test shows they do).
- **Docs:** `RULES_SPECIFICATION.md` terrain table (difficult/dangerous detected along the whole path; area cover = centre inside, plunging fire included, no intervening bonus), `DATA_MODEL.md` (catalog flags, `area` category), `SYSTEMS.md` if it describes the path checks. `assets-src/OPR_TERM_MAPPING.md`: add Rubble Field / Hazard Pool rows.
- **Manual checks:** none (no UI yet).
- **Done when:** all workspaces build and pass, and no `terrainType ===` / `includes` checks for difficult or dangerous remain in `traversal.ts`.
