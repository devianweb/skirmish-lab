# Systems Document

## Overview
This document specifies the concrete implementation details for the rules engine, game systems, combat math, validation, and mechanics. The engine implements OPR-style skirmish rules (Quality/Defense d6 resolution, alternating activations, wound/stun tracking) following Firefight v3.6. No rulebook text is copied; all descriptions here are in our own words.

## Turn Structure: Alternating Activations

Instead of per-player phases, the game uses **alternating unit activations**:

1. The round begins; both players' units are unactivated.
2. The starting player activates one of their units.
3. Players alternate: each activation, the other player then activates one of their own units.
4. When one player has no unactivated units left, the other player activates their remaining units one after another.
5. When all units on both sides have activated, the round ends: cleanup, morale checks, then a new round begins with the player who finished activating all of their units first in the previous round (the opponent of the player who took the final activation).

### Activation State
```typescript
interface ActivationState {
  currentPlayerId: string;      // Who activates next
  roundNumber: number;
  unitsActivatedThisRound: string[];   // Unit IDs
  startingPlayerId: string;     // Who started this round (alternates)
  phase: 'setup' | 'objectives' | 'deployment' | 'activation' | 'round-cleanup' | 'game-over';
}
```

### Setup, deployment and Ambush (14C-2 PR 8; `engine/setup.ts`, `engine/activation.ts`)
A deployment game runs `objectives` -> `deployment` -> `activation`. Every roll comes from the server through `getDiceSpecs` and is attached to the action's log entry (`DiceResolution.outcome.objectiveCount` / `.rollOff`).
- **Objectives phase.** `roll-objectives` (host, no payload) asks for one d6 (`objective-count`) plus the **mission roll-off** (`mission-roll-off`, 20 d6 read as ten host/guest pairs; `resolveRollOff`: first unequal pair wins, an all-tie goes to the host). The count is `objectiveCountFromRoll` (ceil(d6/2)+2). `GameManager` submits it automatically on the host when the phase starts (new match, rematch that has to start over, restored game). Then players alternate `place-objective { position }` from the roll-off winner; `objectivePlacementProblem` checks the board, both deployment zones (`getDeploymentZoneBounds`; the edge counts as inside), more than 9" (`OBJECTIVE_MIN_SPACING`) from placed markers, terrain solids / stairs / ladders, and that a raised `y` is the top of a walkable surface with a supported base. The last marker also carries the **deployment roll-off** (`deployment-roll-off`); its winner becomes `startingPlayerId` and `currentPlayerId` and the phase becomes `deployment`.
- **Deployment.** `deploy-unit` alternates one unit at a time (`advanceDeployment`). Ambush units are never deployable. A Scout may deploy like any other unit, or `hold-scout { unitId }` marks it `heldAsScout` (holding doesn't use the turn unless the player has nothing else to place). When no normal unit is left on either side, `turnState.scoutStage` turns on and held Scouts are placed alternating, starting with the round-1 first player; their zone is `getDeploymentZoneBounds(state, id, true)` (9" past the zone, `SCOUT_DEPLOY_REACH`) and they must stay more than 9" (`SCOUT_ENEMY_MIN_DISTANCE`) from enemy units that are not Scouts. Then round 1 starts with the deployment roll-off winner.
- **Ambush.** At the end of `endRound` for rounds 2 and later `beginAmbushStep` opens `turnState.ambushStep` when a player still has an undeployed Ambush unit: only `deploy-unit` and `skip-ambush` are valid, placement alternates from the player who activates first (`advanceAmbushStep`), then `currentPlayerId` returns to that player. `ambushFootprintProblem`: on the board, clear of terrain, 1" from any model, more than 9" from every enemy unit (12" from one with `repel-ambushers`). A placed unit gets `ambushArrivedRound`; `evaluateObjectives` ignores it that round. A unit still waiting is `isDeployed: false`: it is not activatable (`getActivatableUnits`), not a legal target (`requireTarget`), blocks no movement (the `spatial.ts` unit loops skip it) and holds no objective. Waiting units are alive for `checkGameEnd`, and `summarizeMatch` does not treat them as an unfinished deployment.
- **Setup HUD** (14C-2 PR 9; `client/src/ui/setupPlacement.ts`, `GameHUD`). One placement flow serves all four steps (`currentPlacementKind`: `objective`, `deploy`, `scout`, `ambush`): hovering the board asks the engine's own check (`objectivePlacementProblem`, `validateDeploymentPosition` or `ambushFootprintProblem`) and emits `MarkerSnapshot.placement`, a cursor ring (green when the host would accept the spot, red otherwise) plus circles: 9" around each placed objective, and for a held Scout or an Ambush arrival a circle around every enemy model it must stay clear of (9", 12" from Repel Ambushers; Scouts ignore enemy Scouts). The reason for a red spot is shown in the bottom bar (`.sl-hud-placement-hint`) and, on a click, as a toast; a legal click stages the action in the usual Confirm bar. Deployment zones are shaded during the objectives phase too; a held Scout also shows its wider zone. The panel `.sl-hud-setup-rolls` states the objective roll, the mission roll-off (pairs up to the deciding one, host die first) and the deployment roll-off ("X deploys first") from `GameState.setupRolls`; each roll is also toasted once when it first appears. A waiting player sees "Waiting for X to place objective n of N" and cannot place. A Scout still waiting offers **Deploy now** (just click inside the zone) and **Hold as Scout** (`hold-scout`, confirmed); held Scouts show `HELD AS SCOUT` and are placed in the Scout stage. In the Ambush step the placer picks a unit from the roster (`IN RESERVE (AMBUSH)` rows) and clicks anywhere legal, or presses **Skip (wait for a later round)** (`skip-ambush`, confirmed: a real choice, like the push prompt's "Don't push"). `GameHUD.setupFlow.test.ts` drives two HUDs through objectives, deployment, a held Scout and the Ambush step against the engine.
- **Rematch** (`createRematchState`) passes the placed objectives and `setupRolls` to `applyDefaultScenario` (`restoreSetup`) when the first match finished its objectives phase: it restarts in `deployment` with the same roll-off winner acting; otherwise it starts over in `objectives`.
- **Maps** no longer define objectives: `applyDefaultScenario` ignores `CustomMapDefinition.objectives`, and the objectives phase always runs first, also for a match without the deployment phase: `applyDefaultScenario` starts that match in `objectives` (round 0) with the units already placed (Ambush units too, since nothing sets them aside), and the last `place-objective` goes straight to round 1 activation (`isDeploymentComplete`) instead of deployment. A rematch of such a game keeps the objectives and roll-offs and starts in round 1. `validateAction` rejects `activate-unit` and `hold` for a unit with `isDeployed === false`. Tests that need markers set `state.objectives` directly (or play the phase with `tests/fixtures/setupFlow.ts`).

### Tabletop Maneuver Actions (Phase 6 Engine)
Each activated unit executes one of the tabletop maneuvers:

- **`hold`**: The unit holds its position without moving or attacking, which ends its activation. For a Shaken unit this is its idle activation: it clears Shaken.
- **`advance`**: Spends up to base `speed` (1×), automatically pathfinding around obstacles and other fighters (`findNavPath`). Eligible to shoot a ranged weapon after moving.
- **`rush`**: Rapid double-distance sprint (moves up to 2× `speed` via auto-pathfinding). Ineligible to shoot this activation. Cannot end in melee contact (use Charge instead).
- **`charge`**: Moves up to double `speed` (2×) via auto-pathfinding into melee engagement contact (≤ 1.0" of an enemy model) and **automatically resolves the full melee combat sequence**:
  1. **Attacker Strike:** Attacker attacks with every melee weapon its models carry (Assault weapons included, one resolution per weapon) using server-rolled dice, applying wounds (a model dies at its Tough value; no roll).
  2. **Defender Retaliation:** If the defender survives, it immediately strikes back with all its melee weapons (all its non-Counter ones after a Counter strike). Shaken defenders strike back counting as Fatigued (hits on natural 6s only).
  3. **1" Separation Push-Back:** If both fighters survive, the charger automatically bounces back per model (`pushBackChargerModels`) so every charging model has a ≥ 1.0" edge gap (2.0" center distance) to every enemy model, falling back to a block step with angular fan-out collision avoidance when the per-model spots do not fit.
  4. **No Locked Melee:** Both surviving models become `fatigued` and clear `engaged` status. In subsequent activations, models are never stuck in melee and may freely Hold, Move, Rush, Shoot, or Charge again.
- **`begin-charge` / `charge-leg` (split charges, batch 1D PR 16)**: when no single safe path reaches the target the HUD declares the charge (`begin-charge { attackerId, targetId }`): the host checks the target is within charge reach at the start (straight line from the unit to `chargeDestination`, at most the charge budget), sets `turnState.charge = { unitId, targetId, legs: 0 }` and puts the whole budget (`speed * 2`) in `remainingMovement`. Then `charge-leg { attackerId, path, traversal? }` spends it: the path starts at the unit, is host-checked like a single-model move (budget left, the Difficult Terrain cap on the whole charge, board, `findMoveBlocker` with `keepAway` and only the locked target exempt, `validateDeclaredTraversal` for a jump/fall from an edge, no mid-air / overhang / ladder-rung / overlapping end), and its jump/hazard/fall dice come from `pathTraversalSpecs`, the same helper a move and a one-click `charge` use (the path was validated against the declared traversal, so they agree). A passed jump costs nothing (`pathMovementCost`); a failed one falls and `finishActivation` ends the activation (and clears the charge: no melee). While `turnState.charge` is set `validateAction` allows only `charge-leg`, the final `charge` and `end-activation` (Decision 22: no undo, no other action); the final `charge` must name the locked target, may use only what the legs left, and otherwise resolves as before (strike, strike-back, push-back). `end-activation` abandons the charge. A one-click `charge` with no declaration is unchanged. Squads use the same actions with per-model payloads (see below).
- **Per-model squad charges (batch 1D PR 11)**: for a unit with more than one living model, `charge-leg` and `charge` may carry `modelPositions` (one end spot per living model, in model order), `modelPaths` (each model's path from where it stands; a missing path is a straight line) and `modelTraversals` (a declared jump or fall per model, aligned with the paths). `validateSquadChargeMove` checks every model: the path starts at the model and ends at its position, stays on the board, fits the charge budget left (`remainingMovement`, or the full charge when undeclared) and the Difficult Terrain cap (`pathMovementCost`), is clear under `findMoveBlocker` with `keepAway` and only the target exempt, passes `validateDeclaredTraversal`, and has a legal end (no mid-air / overhang / ladder rung / overlap); the end spots must be a coherent squad that does not overlap itself. A leg must move something. A final `charge` also needs at least one model within `CHARGE_END_EDGE_GAP` of a target model (4" vertically); each other model must end within 0.5" (base edge) of the gap `closestApproach` finds for it (batch 1I PR 32: `engine/closestApproach.ts`, nav paths by `findNavPath` from the model's start within its own remaining distance, ordinary movement only, ranked candidates round up to 6 nearest target models with legal-end and coherency checks; deterministic; `Model N could get closer to the target` otherwise). The helper is written to be reused for the defenders' pile-in (budget 3", target = the charging unit). A 10-model squad checks in a few milliseconds on open ground and under 100 ms for all ten models round a wall. HUD: on a final squad charge the models the player did not place are filled in with `closestApproach` (`autoPlaceChargers`, model order, only already-settled models count as the others) before the host check and are named in the confirmation. A leg adds each model's own path cost to that model's running total (`Unit.modelMovementSpent`, batch 1I PR 30): a model may walk what is left of the charge minus its own earlier legs, and a squad-mate's longer walk costs it nothing; `unit.remainingMovement` is the budget minus the smallest total, so out-of-movement checks still work (see `engine/modelMovement.ts`). A squad that started the leg out of coherency may end it still apart if its coherency shortfall dropped (batch 1I PR 29). Applying a charge puts each model on its spot (`placeSquadModels`; the anchor is the centroid), resolves each model's traversal with the `m<index>_` dice (`applyModelPathTraversals`; a failed jump or fall ends the activation, so there is no melee), then runs the usual pile-in, strike and strike-back. `getDiceSpecs` builds the squad traversal dice with `squadChargeTraversalSpecs` and simulates the move, pile-in and striker count on a copy of the state. A `charge` or `charge-leg` from a unit with more than one living model must carry `modelPositions`: the old single-path block move is rejected ("A squad charge must place every model"). A unit down to one living model sends the plain `path` like any single model (batch 1I PR 27).
- **Per-model push-back (batch 1D PR 11)**: after a melee that leaves both units standing, `pushBackChargerModels(state, charger, foe)` moves each charging model that is within 1" (base edge) of any enemy model straight away from its nearest crowding enemy model until it has a 1" gap; models already clear stay put. The result must be on the board, clear of terrain and models (`findEndOverlap`), reachable (`findMoveBlocker`, target exempt) and keep a coherent squad coherent; otherwise the whole formation steps back along the old anchor line, and the last resort is the old anchor-based `computePushBackPosition`. A spot where any base would overhang (`isBaseOverhanging`) is never used: the step is simply not taken (the unit stays where it is) rather than moving a model off a deck edge. It returns the new anchor (recorded as the outcome's `pushBackPosition`).
- **`shoot`**: Fires an equipped ranged weapon at an enemy target within range and line of sight. Not available while engaged.
- **`end-activation`**: Deliberately concludes the activation, passing initiative to the opponent (or activating remaining fighters if the opponent has none left).

> [!NOTE]
> Following tabletop skirmish rules (OPR Grimdark Future: Firefight), melee combat occurs exclusively via **Charge** maneuvers. Models do not remain locked in base-to-base melee. The obsolete standalone "Fight" button has been removed from the player HUD; the 4 standard tabletop maneuvers are Hold, Move, Rush, and Charge.

### Interactive Reactions & Interruption Framework (Phase 6.5)
In Phase 6.5, the single-actor activation loop expands to support out-of-turn interactive decision prompts (reactions):
- **Melee Retaliation Choice:** Defending players can choose whether to strike back in melee (taking Fatigue) or decline (preserving their fighter's full Quality and fresh state for their upcoming activation).
- **Extensible Architecture:** Powered by `turnState.pendingReaction` in the pure serializable game state, featuring host-authoritative validation, a 15s visual countdown with automatic default fallback on expiration or disconnection, and waiting state feedback for the active player. Designed to support future out-of-turn mechanics (Overwatch, defensive stratagems, Counter, and casualty allocation).

### 2D Visibility-Graph Auto-Pathfinding (`findNavPath`)
Units automatically navigate around terrain obstacles and other fighters rather than halting prematurely:
- Generates clearance waypoints around all impassable obstacle bounding boxes (with unit base clearance `UNIT_COLLISION_RADIUS + 0.12"`).
- Accounts for doorway jambs (allowing passage through the 1.0" center opening of `wall-doorway`).
- Finds the shortest navigable path via visibility graph A* search.
- Applies string-pulling shortcutting and cumulative distance clamping to the unit's remaining movement or double speed allowance.

### Measuring (base edges)
- All rule distances between things go through `shared/src/engine/unitGeometry.ts`: `modelGap(a, b)` (centre distance minus both base radii, floored at 0), `markerGap(model, marker)` (minus one radius), `unitGap(unitA, unitB)` (unit anchors), `edgeGapToCentre(gap)`. Rules are written with the tabletop number: weapon range, the 9" range-gated rules, the 12" hero aura, the 1" deployment gap (every model of the deploying unit, from every model of any other deployed unit, friendly or enemy; `deploymentFootprintProblem` also keeps every model inside the zone and off obstacles, structure solids, stairs and ladders, and `settleSpawnPositions` uses it to move pre-placed units off terrain when the deployment phase is off), objective control 3", coherency 1" / 3" / 6" (`SQUAD_COHERENCY_*_EDGE`; the `_CENTRE` constants are derived), engagement `ENGAGEMENT_EDGE_GAP` (0.5"), charge end `CHARGE_END_EDGE_GAP` (0.25"). Path lengths stay centre-based. `MODEL_OVERLAP_DISTANCE` (0.9" centre) is a physical overlap check, not a rules range. The HUD range ring for shooting is drawn at weapon range plus one base radius from the model centre; the objective ring is unchanged.

### Melee Engagement Contact Visualization
- When moving or charging into melee engagement (base edges ≤ 0.5"), the path line reflects contact in bright orange/crimson and renders a pulsing contact disc.
- A distinctive glowing double-ring melee marker (`0xff5252` and `0xffab40`) highlights the opposing enemy fighter under threat.

## Combat Resolution (Quality / Defense)

All rolls are d6 checks against a target number, where **lower is better** for both stats:

### 1. To-Hit Roll (Quality)
- For each attack, roll one d6.
- A result **equal to or greater than the attacker's Quality (Q)** scores a hit.
- Example: a fighter with Q 3+ hits on a roll of 3, 4, 5, or 6.

### 2. Defense Roll
- For each hit, the defender rolls one d6.
- A result **equal to or greater than the defender's Defense (D)** blocks the hit.
- Example: a fighter with D 4+ blocks the hit on a roll of 4, 5, or 6.
- Cover and special rules may modify the effective D value.

### 3. Apply Results
- Each unblocked hit causes a **wound** (or, where specified, a **stun**) on the target fighter.
- Fighters removed from play when their wounds are depleted.

### Resolution Table
```
Attacker: roll d6 >= attacker Q  -> hit
Defender: roll d6 >= defender D -> hit blocked
Unblocked hit                    -> wound (or stun)
Fighter wounds <= 0              -> casualty (removed)
```

## Wounds & Shaken
- Each model has a Tough value (1 unless it has `tough(X)`). `Model.wounds` counts down from `Model.maxWounds`; each unblocked hit is one wound and the model is removed when it reaches 0. There is no trauma roll or wound-effect table. `applyWounds` (actions.ts) fills the picked model before the next one and is used by falls and move hazards; attack wounds use `allocateWounds` (casualties.ts), which always continues on the most wounded living model first (ties by list order), then the owner's next ordered pick, else the first living model; the owner assigns wounds in squads (`pick-casualties`).
- **Shaken:** the single non-lethal suppression state. A Shaken unit may be activated but can only end its activation idle (`validateAction` rejects everything else, `requireActiveUnit` and `validateActionBasic` alike); `finishActivation` removes Shaken from the active unit. It always fails Morale Tests, strikes back as Fatigued, and cannot seize or contest objectives (`isUnitInObjectiveRange`).

## Morale
Morale is tested at the end of an **activation** (14C-2), not at the end of the round, and there is no army-breaking test (`isArmyBroken` / `applyRoundEndMorale` are gone).
- `beginActivation` records `turnState.woundBaseline` (`recordWoundBaseline`, each living unit's total wounds). `finishActivation` asks `getUnitsRequiringMorale` for every unit (either side) whose wounds dropped, that was not in `turnState.meleeUnitIds`, and that is at half strength or less (`isAtHalfOrLess`: models x 2 <= starting models, or wounds x 2 <= Tough for one model).
- `getDiceSpecs` for `end-activation` requests one `morale` d6 per testing unit that is not already Shaken and one `fearless` d6 per Fearless testing unit. Actions that can wound the mover and end its activation themselves (a move or charge that may fall, a hold in dangerous terrain) add one spare `morale` die (and one `fearless` for a Fearless mover): `selfMoraleSpecs`.
- **Melee results (14C-2 PR 2):** `markInMelee` records the fighting pair in `turnState.meleePairs`. `getMeleeResults` compares, per pair, the wounds each unit lost since `woundBaseline` plus the enemy's Fear (X per living model, once per unit); `getUnitsRequiringMorale` returns the wound-test units followed by the melee losers, so `getDiceSpecs` and `applyEndOfActivationMorale` use one list (same `morale`/`fearless` dice). A melee loser that fails while `isAtHalfOrLess` is Routed (all models removed, status `routed`, record outcome `'routed'`). `finishActivation` logs the results as `dice.outcome.meleeResults` (ties included).
- `applyEndOfActivationMorale` runs each test with `resolveMoraleTest` (Quality test, Hero within 6" lends its Quality, Fearless 4+ saves a failure, a Shaken unit fails automatically): a failure makes the unit Shaken. The tests are attached to the log entry as `dice.outcome.moraleTests`.
- **Hold the Line (14C-3 PR 1; data-driven, Hive Bond will share it).** `DISTANT_ATTACK_MORALE_TRAITS` (`rules/traits.ts`) lists the faction rules that give +1 to Morale Test rolls when the unit was shot from over 9" or charged from over 6". The distance is the attacker's `unitDistance` to the target (the same base-edge measure that shooting range and charge reach use) taken when it happens: a `shoot` stores it per target in `turnState.attackedFrom[targetId].shot`, `begin-charge` (or a one-click `charge`, before the move) stores `.charged`. `applyEndOfActivationMorale` passes it to `resolveMoraleTest` (`distantAttackMoraleBonus`: strictly over 9" / 6"), and the `MoraleTestRecord` carries `modifier` (the HUD shows "roll +1"). `attackedFrom` is cleared when the activation ends. Rules are unit-level in the engine (like Fearless), so "most of the unit's models have the rule" is true exactly when the unit carries it. Per-model rules wait for Army Forge import (Phase 16); all four lists give every model of a unit the same rules. A unit that takes spilled Blast hits counts as shot too (Decision 5d): when the (auto or chosen) split gives it at least one hit, `attackedFrom[spillUnit].shot` is `unitDistance(shooter, spillUnit)`; a unit within 3" that gets zero hits is not recorded.
- **Bad Shot and Ferocious (14C-3 PR 2; Orc Marauders).** Both live in `engine/combat.ts`. Bad Shot is a -1 hit modifier for non-melee attacks in `computeCombatModifiers` (listed as "-1 Bad Shot"; a natural 6 still hits, Unstoppable still negates it). Ferocious is one of the per-6 bonus hits that `bonusHitsPerSix` adds up with Surge, Relentless and Furious (`ferociousApplies`): shooting needs `distance > 9`; a charge needs `chargedFrom > 6`, where `chargedFrom` is `turnState.attackedFrom[targetId].charged` (the distance noted when the charge began, the same figure Hold the Line uses) passed to `resolveStrikes`; an unknown start distance means no bonus. Dice are sized for the worst case (`'any'`), so a charging Ferocious unit may roll more defense dice than it uses. Extra hits are plain hits: only the original hit (and its Blast copies) gets Rending / Rupture AP. The log outcome carries `bonusHits`, and the dice panel appends "(incl. N extra from 6s)" to the hit count.
- Fight, charge strike and strike-back mark both units with `markInMelee`; until the melee-result rule lands (14C-2 PR 2) units in melee get no Morale Test.

## Weapon Profiles
Weapons are data-driven profiles:

```typescript
interface WeaponProfile {
  id: string;
  name: string;
  type: 'ranged' | 'melee';
  range: number;              // Inches; melee typically 1 (engagement range)
  attacks: number | string;   // Flat number or dice expression ('D3', '2D6')
  specialRules: string[];     // Special rule IDs from the ruleset data
}
```

Hit and wound capability come from the **fighter's Q**, and the target's survival from its **D** — weapons primarily vary by range, attack count, and special rules (e.g., armor-piercing modifications to the Defense roll, extra damage, blast effects).

### Range Brackets
- Weapons are usable up to their listed range.
- Range brackets (e.g., long-range penalties) are defined as special rules in ruleset data where applicable.

## Special Rules Framework
Special rules are data definitions, not hardcoded logic where possible:

```typescript
interface SpecialRuleDefinition {
  id: string;                 // e.g., 'ap1', 'relentless', 'impact'
  name: string;              // Original short label
  description: string;       // Our own words (never rulebook text)
  modifiers?: RollModifier[];
  hooks?: RuleHook[];        // e.g., 'on-hit', 'on-charge', 'before-activation'
}
```

- **Roll modifiers** adjust Q/D checks (e.g., AP reduces the target's effective D).
- **Rule hooks** attach effects to engine events (charge, hit, casualty, round start).
- The engine ships with a core set of generic special rules; rulesets select from them and may define more.

### Special rules in the engine (14C-2 PR 7)
`shared/src/engine/specialRules.ts` holds the small helpers the host and the HUD share: `getEffectiveSpeed` (Speed +2" Fast / -2" Slow; Rush and Charge are twice it; every distance check uses it, never `unit.speed`), `isMeleeWeapon` / `findMeleeWeapon` / `hasMeleeWeapon` (a ranged weapon with `assault` also strikes in melee; a true melee weapon is preferred), `findCounterWeapons` (every equipped Counter weapon), `findNonCounterMeleeWeapon` and `impactDiceCount`. **Per-model loadouts and all-weapons melee (14C-3 PR 1B):** `FighterDefinition.modelLoadouts` (weapon ids per model; length must equal `modelCount`) spawns a unit whose `weapons` are the distinct ids and whose models record their own `weaponIds` (absent = carries all, so armies without it behave as before). A weapon's attacks are multiplied by the living models that carry it and qualify: `firingModels` (range and sight per model, carriers only) for shooting, `strikingModelCount(striker, foe, weaponId)` (3" reach) for melee. The host rejects a shoot allocation for a weapon no living model carries. Melee (`fight`, the charge strike, the strike-back, the pile-in strike) strikes with **every** melee weapon (`meleeWeaponSlots`: equipped, Assault included, equipment order) that has a carrier in reach; the payload `weaponId` of `charge` / `fight` is accepted for compatibility but no longer chooses a weapon. Each weapon has a fixed slot in that list and its own dice batch: slot 0 keeps the plain `to-hit` / `defense` / `regeneration` purposes, later slots are prefixed `w1-`, `w2-` (a slot whose carriers are all gone, or out of reach, rolls and resolves nothing and never renumbers the others, which keeps the up-front dice of a casualty pause valid: the resume counts the survivors per weapon). A strike-back numbers its batches in striking order instead (`strikeBackEntries`). Counter weapons keep `counter<i>-` with `i` their place among all the unit's Counter weapons. Impact is the unit's X for each model in reach plus each weapon's own X for each carrier in reach. The dice outcome keeps the totals (sums over every weapon, so the melee result counts all of them) and adds `outcome.meleeStrikes`: one `WeaponAttackOutcome` per weapon that struck, in order; the strike-back prompt's `data.weaponIds` lists the weapons it will use (`data.weaponId` is the first). **Charge order** (`resolveChargeStrike`, staged `impact` -> `counter` -> `strike`): the charger's Impact(X) hits (X dice per striking model, dice `impact`, `impact-defense`, `impact-regeneration`; none while the charger is Fatigued), then the charged unit's Counter strikes (`counterStrikeWeapons`: every Counter weapon with a numeric attack count, none while the unit is Fatigued, Shaken or destroyed; one resolution per weapon with dice `counter<i>-to-hit`, `counter<i>-defense`, `counter<i>-regeneration`, wounds attached as `counterStrikes`), then the charger's own strike if both units still stand. After Counter strikes the defender's strike-back is offered for `findNonCounterMeleeWeapon` only (no prompt without one, so the step back follows); without a Counter strike it is the default melee weapon as before (a Shaken Counter unit can strike back with its Counter weapon, as Fatigued). The charger being wiped out by Counter ends the exchange in the defender's favour (consolidation). **Casualty pauses (14C-2 PR 7B):** the dice are rolled up front for the full strike counts (an upper bound). When Counter wounds remove models from a surviving squad charger, or Impact wounds remove models from a surviving squad that is about to Counter, `deferCasualties` raises the owner's `pick-casualties` with the continuation `charge-resume { stage, attackerId, targetId, weaponId, chargeDistance, dice, counterStruck? }` (plain data; the dice ride in the reaction). Accepting the pick (or the timeout auto pick) calls `resumeChargeStrike`, which runs `resolveChargeStrike` from `stage` over the survivors: attacks are counted from the models in reach after the pick and the unused extra dice are ignored. The resumed part is logged on the pick's own entry (its `dice` carry only that part's outcome: `counterStrikes` or the strike). The final strike keeps the `charge-strike` continuation. **Fear** (`fearValue(unit, foe)` in `activation.ts`): X per living model of the Fear unit within melee reach (`strikingModelCount`, 3") of the enemy it is compared with, at least one, measured when `getMeleeResults` runs. **Shred** (`resolveAttack`): each unmodified Defense roll of 1 adds one plain wound (`CombatOutcome.shredWounds`, applied after the Deadly-multiplied wounds by `applyOutcomeWounds`). The dice are sized by `chargeExtraSpecs`, shared by the charge and the pile-in strike. `DiceResolution.outcome` carries `impact`, `counterStrikes` (`SpecialStrikeOutcome[]`) and `shredWounds` for the dice panel and log. **HUD (14C-3 PR 1C, `client/src/ui/loadout.ts`):** the unit list and data card show each carried weapon with a `N×` prefix (living models carrying it; shown when the unit has more than one living model; a weapon with no living carrier is not listed), the shoot panel offers only carried ranged weapons and each chip counts the firing models with the same `firingModels` the host uses, there is no melee weapon choice (the charge confirmation lists every melee weapon and its attacks; `weaponId` is still sent as the first one), the dice panel renders a To-Hit / Defense block per `outcome.meleeStrikes` entry when several melee weapons struck (each from its own `w<slot>-` dice and its own target numbers and AP), and `specialStrikeLines` prints one log line per entry.

**Activation test casualty pick (Decision 42):** `applyActivationHazard` records the test's wounds in a wound ledger; when a squad survives with fewer models, `deferCasualties` raises the usual `pick-casualties` reaction with the continuation `{ kind: 'activation-hazard', attackerId, finish? }`. On `activate-unit` the activation simply goes on after the pick; on a one-action `hold` the continuation carries the action's dice (`finish.dice`) and `finishActivation` (morale, Shaken cleared, next player) runs after the pick. A destroyed or single-model unit gets no prompt.

## Action Validation (Host-Side)

All actions are validated by the host. The guest never trusts its own validation for legality — it's only for UX.

### Validation Checks
```typescript
interface ValidationContext {
  state: GameState;
  action: GameAction;
  actorId: string;
}

function validateAction(ctx: ValidationContext): ValidationResult {
  // 1. Activation legality (is it the actor's turn to activate)
  // 2. Actor ownership (unit belongs to acting player)
  // 3. Unit not yet activated this round
  // 4. Unit not Shaken/routed (a Shaken unit may only end its activation) (or per special rules)
  // 5. Movement distance vs speed allowance, terrain, obstacles
  // 6. Line of sight and range (for shooting)
  // 7. Engagement rules (melee range, who can fight)
  // 8. Weapon availability on the fighter
  // 9. Game state prerequisites (phase, round state)

}
```

### Common Validation Rules
- **Turn Ownership:** Action actor must be the currently-activating player
- **Unit Ownership:** Unit must be owned by acting player
- **Activation:** Unit must not already be activated this round
- **Line of Sight:** Check LOS where required (shooting)
- **Range:** Check weapon range for shooting
- **Movement:** Validate distance, terrain, obstacles
- **Engagement:** Respect engagement/fight rules

## Dice System

### Server-Rolled Dice Flow
1. Host needs dice rolls for resolution
2. Host requests rolls from the signaling server with a unique rollId
3. Signaling server generates results using its RNG
4. Server broadcasts results to both peers simultaneously
5. Both peers receive results; host applies resolution deterministically
6. Results are part of the resolution and included in the state update

```typescript
interface DiceResolution {
  rollId: string;
  purpose: string;           // 'to-hit', 'defense', 'morale'
  specs: DiceSpec[];
  results: DiceResult[];
  context: {
    attackerId?: string;
    targetId?: string;
    weaponId?: string;
    actionId: string;
  };
}
```

### Dice Modifiers
Track all modifiers to rolls:
- Quality modifiers (to-hit)
- Defense modifiers (cover, AP)
- Re-rolls where special rules provide them

### Phase 5 Implementation (as shipped)
- Dice specs are computed by the host (`getDiceSpecs` in
  `shared/src/engine/actions.ts`): `attacks` to-hit dice plus `attacks`
  defense dice, all d6. Dice-expression attack counts (e.g. `D3`) are
  rules-engine territory (Phase 6) and rejected in Phase 5.
- Defense dice pair with **hits** in order: the 1st hit uses the 1st
  defense die, the 2nd hit the 2nd, etc. Defense dice beyond the number of
  hits are unused. Both peers see the full roll, so this is transparent.
- **Cover:** a defender with `in-cover` status imposes +1 on the effective
  Quality needed to hit them (cover makes targets harder to hit).
- The host validates an action *before* requesting dice, so illegal actions
  never spend a server roll. The resolution (`DiceResolution`, including
  the derived outcome) is attached to the action log entry and broadcast in
  the state — both players' dice displays read from state, never from
  local rolls.
- **Resilient Dice Roll Requests:** `SignalingDiceProvider` retries roll
  requests every 2 seconds (up to 3 retries) and reconnects on demand
  (`ensureConnected()`). The signaling server caches recent roll results by
  `rollId` (`room.rollCache`), ensuring retries are strictly idempotent.

## Line of Sight, Cover & Apertures

### LOS Rules
- **Standard Checks:** Line of sight is drawn directly between attacker and target on the board plane.
- **Sight-Blockers:** Blocked by solid terrain with `blocksLineOfSight: true` (e.g. solid walls, columns) and by other living fighters (`LOS_UNIT_RADIUS = 0.4`).
- **Apertures (Windows & Doorways):**
  - **Doorways (`wall-doorway`):** A doorway is open air between two jambs under a lintel (1.5" wide × 2.25" tall opening on a 4" wall). Line of Sight and movement pass freely; there is no port, so standing in a doorway gives no cover by itself. A model tucked behind a jamb gets ordinary sight-blocker cover.
  - **Windows / Firing Ports (`wall-window`, ruin ports):** Windows block model movement. A ray that goes through the aperture is allowed only if at least one model (shooter or target) has its base edge within 1.0" of the opening ("manning the port"). A defender manning a port that the shot passes through gains +1 Defense (Cover). If both models are further away, the aperture blocks sight (preventing distant keyholing); rays that clip the sill or lintel are blocked as ordinary solids.

### Terrain Structure: Solids + Apertures
Terrain pieces resolve to **solids** (walls, jambs, sills, lintels, columns) and **apertures** (window firing ports); see [DATA_MODEL.md](./DATA_MODEL.md). The engine reads only those boxes, with no per-building special cases:
- **Movement:** solids with `isObstacle` block, by their height range (a lintel above head height does not block walking beneath it). **Step-over:** a piece whose obstacle solids all rise no more than `STEP_OVER_MAX_HEIGHT` (1.0") above the floor it stands on and that has no floor, stairs or ladder (`isStepOverPiece`; barricade, crate, pipe, or any custom piece meeting it) does not block movement: `findMoveBlocker`, `clampMoveDestinationWithObstacles` and the nav obstacle corners skip it, so a path goes straight over at straight-line cost. Height is measured from the piece's own base, so a barricade stacked on a deck is stepped over by a model on that deck. `findEndOverlap` still treats it as a solid (no ending on it), and cover and line of sight are untouched. Doorway gaps and the open courtyard of an L-corner ruin are walkable; window sills and apertures are not.
- **Line of Sight (3D):** rays run from the attacker's eye (`EYE_HEIGHT` = 1.1" above its feet) to the target, sampled at head (1.1"), torso (0.6") and feet-top (0.1"). The target is visible if **any** sample ray is clear (one yes/no result). A ray is blocked by a solid it crosses at that height, or by an aperture it passes through unless the shooter or target is **manning** that port.
- **Manning:** any model's base edge within 1.0" of the port box (centre within `MANNING_REACH + UNIT_BASE_RADIUS` = 1.5"; squads are tested per model).
- **Elevation is geometry:** there are no "setback blind spot" or "parapet" special rules. A deck is a solid slab (top at 3.0"), so a close ground shooter cannot see a model standing back from the deck edge (the deck is in the way), while a distant shooter can see over the edge because the angle clears it. A model at the very edge is partly hidden by the slab and gets ordinary sight-blocker cover from it only when the shooter is close; cover on a deck edge comes from stacking low cover (a barricade or crate) or a wall on the deck. An elevated shooter cannot see a target hugging the base of the deck because the floor is in the way.
- **Partial squad moves and coherency at activation start:** the squad move/rush check in `validateAction` only needs final positions, and a model whose path is missing, `[start]` or `[start, start]` costs 0" and passes every per-model check, so the HUD's early **Confirm move** (`finishSquadMove`, unstaged models keep their position with a one-point path) needs no new payload. `incoherentStartBlock` (in `actions.ts`) makes `hold`, `end-activation` and a `shoot` made without having moved fail for an incoherent squad that has not moved or attacked (Shaken units exempt); the HUD disables Hold and Shoot and shows a hint (batch 1I PR 29). `isUnitInObjectiveRange` checks each living model's base edge for multi-model units and ignores the unit anchor.
- **Squad coherency:** `validateSquadCoherency(positions)` links models in pairs and, since batch 1I PR 28, requires the links to form one connected group (step 3, a flood fill with the same level-aware limits and 0.02" tolerance; otherwise `reason` reads "Squad is split into N groups (models ...)" and the HUD staging toast shows it). Each model must also link to at least one other (checked first, so a lone stray is named by number). The link limits are: 2.0" centre to centre on one level (`SQUAD_COHERENCY_SAME_LEVEL_CENTRE`, 1" base gap) or 4.0" when the pair differs in height by more than `SQUAD_LEVEL_DIFFERENCE` (0.5", `SQUAD_COHERENCY_CROSS_LEVEL_CENTRE`, 3" base gap). The 6.0" whole-squad horizontal spread (`SQUAD_COHERENCY_SPREAD`) is unchanged. `coherencyShortfall(positions)` (batch 1I PR 29) is the matching distance-to-coherent: Prim's minimum spanning tree over all pairs with edge weight 0 inside the link limit (+ tolerance) else `d - limit`, plus the widest pair's excess over the spread; it is 0 exactly when the squad is coherent. `isRegroupingMove(before, after)` is true when `before` was incoherent and the shortfall dropped by more than `COHERENCY_REGROUP_MIN_GAIN` (0.05"). `squadEndCoherency` in `actions.ts` uses it for move/rush end positions and squad charge/leg ends (positions before the action = the unit's current living-model positions), and the HUD staging uses the same helper (a regrouping squad skips the per-placement spread toast and is judged as a whole when the last model is placed or on early Confirm). Positions carry y; the host's move/rush validation and the HUD's last-model staging check call it, and the mid-air guard already stops a client forging y. The constants are centre distances; batch 1D's edge-measuring conversion will rename them.
- **Drops, jumps and movement cost:** movement is measured along the board. A descent of more than 0.5" that is not a stair, ramp or ladder is a *drop* and costs only its horizontal distance (`pathMovementCost`); climbs, stairs, ramps and ladders cost their full length. Drops of 3" or less are regular movement (no test). Drops of 3-6" must be jumped: roll one die per started inch (`calculateJumpDice`, `ceil(distance - 0.05)`), each needing 2+ (`JUMP_TARGET`; a Strider rolls half the dice, rounded up; Flying auto-passes); if every die succeeds the model lands with no damage and the activation continues, otherwise it falls (activation ends). **One roll per unit:** the host makes a single `jump` roll for a leg, sized by the *leader's* declared crossing (`planLegJumps` in `actions.ts`; the leader is `payload.jumpLeader`, a living-model index that must declare a jump, default the lowest-index jumper; a certain fall over 6" still belongs to the longest such model); on a failure the leader falls from its take-off and, when the fall is 2" or more, `gatherAroundFallen` places every other living model within 1" (edge to edge) of it at the bottom (no dice; around the landing spot if it died); a shorter fall leaves the other declared jumpers at their take-off. **Falls** of 2" or more (`fallDiceCount`) roll one `fall` die per started inch fallen; each 1-3 is one wound (`countFallWounds`), no Defense roll; the wounds belong to the model that fell (`applyFallWounds`): it takes them until it dies and any excess is lost, never carried to the rest of the squad (also for a push off an edge). Drops above 6" cannot be jumped and always fall (no jump roll). Horizontal gaps use the identical test (`measureElevatedGap` finds the widest run of open air along an elevated path; touching decks are not a gap; over 6" the host rejects the move). Every jump, fall and dangerous-terrain roll is attached to the action's log entry (`DiceResolution.outcome.traversal`) and shown in the dice panel and log. A drop needs clear air below the model's base: the fall column (a base circle of `UNIT_COLLISION_RADIUS` swept from the take-off height to the landing height, `isFallColumnBlocked`) is checked in `findMoveBlocker` for vertical drops and for near-vertical slides (under 0.7" across), so a model cannot fall through a deck slab, the stair wedge or scatter. Models step fully off the edge (`DROP_STANDOFF` = 0.55") at floor height first, then fall; that horizontal step is measured like any other movement, and the nav only offers drop spots as an air point plus its ground twin (never a stepping stone for climbing). A stair segment only counts as "on the stairs" when it follows the slope surface (within ~0.3" of `getStairSurfaceHeight`); anything else is collision-checked against the wedge body, and the nav's planning cost uses the free-drop (horizontal-only) rule. Movement cost is always measured with the moving unit (`pathMovementCost(state, path, unit)`): without it a Flying model's path across a gap read as a free jump and the HUD refused it. A move never ends with the model hanging in mid-air: the nav path stops at the edge if the budget cannot finish a drop, and the host rejects any move that ends suspended (`isSuspendedInMidAir`). Stair orientation is data: the top (head) end is always local +Z, so the mesh, the F9 wireframe and the physics always agree. Ladder paths walk to the ladder foot (`LADDER_STANDOFF` = 0.55" off the deck face, on the ground), climb straight up the climb line above the foot, then step onto the head spot (0.55" in over the deck). The foot/head step is free (`isLadderStepSegment`, in both the nav clamp and `pathMovementCost`); only the vertical climb counts and is all-or-nothing. `isSuspendedInMidAir` is false only for points on a ladder's climb line (`isOnLadderClimbLine`), so the guard stays on for the rest of a map that has ladders; the host also rejects ending anywhere on the climb line above the foot. **No overlapping ends:** a model never ends a move overlapping terrain or another model. `findEndOverlap(state, unitId, point)` reports an obstacle solid whose height span overlaps the body (`y+0.15` to `y+EYE_HEIGHT`, so the floor stood on and lintels overhead don't count) within `UNIT_COLLISION_RADIUS` of the point, or a living model of another unit within `MODEL_OVERLAP_DISTANCE` (0.9") at a similar height (|dy| < 1.0; squad-mates have their own check; base-contact charges end at about 1.0"). The host checks it next to the mid-air guard for move, rush (single and every squad model), charge, and a declared jump's landing (`findJumpOption` offers no such jump). `settleMoveEnd` is the standalone pull-back. **No overhanging ends:** `isBaseOverhanging(state, point, surfaces?)` is true for an elevated point (y > 0.3) when the centre or any of 16 samples round the base circle (`UNIT_COLLISION_RADIUS`) is not over a walkable floor within 0.3" of the model's height. Floors are a union (`findWalkableSurfaceIn`), so a base across a flush seam is supported; stair slopes and ladder arrivals count as support (a slope supports a base whose rim sits within 0.3" plus radius x grade of the model's height, so a model can stop part-way up a stair slope; a stair's foot is its own base height, `piece.position.y`, so stairs standing on a deck work like ground stairs); the ground is not judged. The host checks it beside `isSuspendedInMidAir` for move, rush (single and every squad model) and charge, and `findJumpOption` offers no jump whose landing overhangs. `settleEnd` treats it as a bad end: if the path's last leg is the level step off a climb's top, it first pushes the end on along that step to the first spot (plus 0.05") where the base is clear of the lip, provided `pathMovementCost` stays within the budget (`stepFullyOntoFloor`); otherwise it pulls back (a climb is all-or-nothing, so a model that cannot afford the extra stops at the stand-off spot). The direct-line fast path of `findNavPath` is settled too. The client's `snapCursorToEdge` puts a deck-side cursor `UNIT_COLLISION_RADIUS + 0.05"` inside the edge, and `isAtFloorEdgeToward` accepts a model up to 0.55" inside an edge so the jump/fall offer still works from that spot. **Labels:** `classifySegment(…, prev, next)` reports the short level step off a climb's top (`prev` is a rise) or off an edge before a drop (`next` is a fall from `b`) as `walk`, not `gap`; the preview then reads just "climb 3.0\"" or "drop 3.0\"". **Failed jumps:** the model falls from the jump's take-off point (the declared one, else the start of the first jump segment) to where `findFallLanding` puts it: the highest walkable floor below the take-off floor under the take-off point, else the ground, at the nearest spot (searching outward to `FALL_LANDING_RADIUS` = 2") with no `findEndOverlap` and no `isBaseOverhanging` (a walked-off drop over 6" stays where the player declared the landing). Fall wounds apply from `FALL_DAMAGE_MIN` (2") using the real height. In a multi-model unit the faller moves first and takes the fall wounds; on a fall of 2" or more the rest of the unit is then gathered round it (`gatherAroundFallen`), on a shorter fall the other declared jumpers stay at their take-off (`stopJumperAtTakeoff`). The activation ends. **The jump is free after moving:** `findJumpOption` and the host's `pathMovementCost` charge a hop nothing, so only the walk to the take-off edge is checked against a model's remaining move (single models, squad followers via `planFollowerCrossing`, charge legs); the HUD never clamps a landing to the ring. **Flying paths:** a Flying unit's move is the straight line from its start to its stop spot, costed by `pathMovementCost(state, path, unit)` (a rise costs its 3D length, a descent its horizontal distance). `findMoveBlocker` ignores terrain and other units along a Flying path and checks only the final spot: no base overlap with another unit (at a similar height) and, with `keepAway`, the 1" keep-away (a model that began closer may not end closer); the host still rejects an unsupported, overhanging or overlapping end. `findNavPath` therefore takes its direct fast path for Flyers and never routes them via stairs. When no route exists, its fallback shortens the straight line until it no longer runs through terrain or a stair wedge (units are handled by the end-spot pull-back). **Rush stop reasons:** the HUD names why a Rush ends below a higher target (`rushStopReason`): out of movement, difficult ground, "blocked by another unit" (the same plan with every other unit removed would reach that height, `routeBlockedByUnits`), else height (stairs or a ladder are needed). **Hover cost:** the HUD memoises hover `findNavPath` plans per 0.1" cell and state object (`hoverNav`); clicks always replan. **Dice order for a move:** `jump` (untagged, one per leg), `fall` (sized by the faller's fall height, rolled up front and unused if the jump passes), the hazard dice, then the spare `morale`/`fearless` dice (PR 1).

**Pushing (`engine/push.ts`):** at the end of an activation `finishActivation` finds the tested units an enemy attacked (`pushAttackerFor`), takes one `push` die for each that became Shaken (the `end-activation` dice request has one `push` die per such tested, not-yet-Shaken unit), and on a 4+ sets the pending reaction `push` for the attacker (several are chained through `PushData.rest`). `autoPush` picks the model nearest the attacker and walks 2" away from it in quarter-inch steps back to the first legal spot (`planPush`: within range, on the board, no `findEndOverlap`, no overlap with a squad-mate; overhanging an edge makes it fall to `floorHeightBelow`); `regroupAfterPush` moves only models cut off from the pushed one. When the pushed model falls with dice (drop of 2" or more), `gatherAroundFallen` instead places every other living model at the bottom within 1" (edge to edge, 2.0" centre) of the fallen model, each on the legal spot (supported, clear, not overlapping) closest to where it stood; nobody's activation ends. The reaction offers three options: `auto-push` (default; the host applies it on the 30 s timeout), `confirm-push` (HUD only: it opens the pick-a-model-and-spot mode and is rejected as a `respond-reaction` answer) and `no-push` (Don't push: the attacker declines, nothing moves; the one agreed exception to the Auto + Confirm rule). `push-move { modelId, destination }` is the custom choice (host recomputes the height). The attacker's HUD (`GameHUD.pushContext`) shows the 2" ring around the picked model, previews the clamped spot with a "falls N\"" note from `planPush`, and sends `push-move` only after a local `validateAction`; the opponent sees the generic "Waiting for opponent: Push". Fall dice for a pushed fall are requested by `getDiceSpecs` for the answering action.
- **Difficult / dangerous / area terrain (13.6E PR 1):** `isPathDifficult` / `isPathDangerous` (`traversal.ts`) test every path segment against every flagged piece's footprint at the piece's level (`segmentCrossesFootprintAtLevel` in `spatial.ts`: footprint plus the 0.15" margin, with some part of the segment inside it between the piece's base - 0.25" and its top + 0.6"), using `isDifficultPiece` / `isDangerousPiece` (piece flag, then catalog default, then a legacy type list); the engine names no terrain types for these rules. The Rush/charge planner's `stopBeforeDifficult` uses the same test (`findEnteredDifficultPiece`), so it stops before a difficult piece it would cross, not only one it ends in. **Dangerous terrain test (14C-2 PR 6):** a unit tests once per dangerous piece per activation, with one die per wound it would take to destroy it (`woundsToDestroy` in `traversal.ts`: living models' remaining wounds summed). `dangerousPieceIdsUnderUnit` (pieces any living model stands in) feeds `getDiceSpecs` for `activate-unit` (and a `hold` that starts the activation); `dangerousPieceIdsOnPaths` (pieces the move's paths cross, Flying none) feeds `pathTraversalSpecs` for Advance, Rush and charge legs, which skips pieces already in `Unit.hazardTestedPieceIds`. Each piece's dice have the purpose `hazard_<piece id>`. `resolveHazardTests` rolls every untested piece the unit has dice for, records one `hazard` traversal event per piece (dice count, rolls and wounds, shown in the log), wounds the unit through `applyWounds` (the move's `casualtyModelIds` priority when given) and marks the piece tested; `beginActivation` clears the list. A model that fell in a leg does not count its path. The client needed no change: `GameManager` requests whatever `getDiceSpecs` returns. **Area cover:** `findCoverSource` handles `isAreaPiece` pieces first: cover only for a target inside the footprint at its level (whole base for a unit of several living models, centre for a lone model), whatever the line of fire, and never the intervening low-cover bonus.
- **Traversal classification and declared jumps (batch 1E):** `classifySegment(state, a, b, unit?, prev?)` (`engine/traversal.ts`) is the one place that says how a straight stretch of a path is traversed: `walk | stairs | ladder | climb | drop | gap | jump-drop | jump-gap | fall | blocked`, with its movement cost, height, gap/drop distance and jump dice (one per started inch, 2+, half for Strider; Flying is always `walk`/`drop`). Thresholds: a descent of 3" or less is a `drop` (cost: horizontal only), 3-6" a `jump-drop`, over 6" a `fall`; a level run of open air (elevated, nothing to stand on) of 1" or less is a `gap` (ordinary), 1-6" a `jump-gap`, wider is `blocked`; a sheer rise of 3" or less is a `climb` only when `canClimbBetween` allows it (the top is the height of a floor of a climbable piece, `isClimbable` = piece `climbable` override, else the catalog default, else false; the foot of the climb is within a base-off stand-off of that floor; and the fall column above the foot is clear, `isFallColumnBlocked`, a climb being a drop in reverse), otherwise `blocked`; a rise over 3" is `blocked`. The host (`validateDeclaredTraversal` -> `validatePathClimbs`) rejects any path with an upward step that classifies as `blocked`. A descent that also crosses more than 1" of open air (`measureElevatedGap` over the segment, the same measure `detectPathGapJump` uses) is a `jump-gap` whatever its height change. **Jump distance is the straight-line 3D length of the hop (take-off spot to landing spot), for `jump-gap` and `jump-drop` alike** (`SegmentClass.distance`; `detectPathGapJump().gapDistance`; `detectPathFall().maxDropDistance`): dice come from it (`calculateJumpDice`), and a gap hop longer than 6.05" is `blocked` (also when it drops; never a `fall`). A pure drop keeps its height for classification and fall damage (3" drop, 3-6" `jump-drop`, over 6" `fall`) but its dice use the hop length (height plus the step-off). A hop that is already a gap jump is one jump (no second drop test). So `classifySegment`, `detectPathGapJump`, `findJumpOption` and `validateDeclaredTraversal` always agree; with 1" or less of open air a 3" drop stays a free `drop`. A passed jump (`jump-drop`, `jump-gap`) costs 0 movement. `pathMovementCost`, `detectPathFall`, `describeDrop` (via `classifyDropHeight`) and the nav's edge costs all read it, so the host, the HUD and the pathfinder agree. `prev` lets a straight 3" fall at a ladder's column be a plain `drop` unless the model arrived by the ladder's head step (then it is the ladder descent).
  - **`findNavPath` plans ordinary movement only:** its graph contains only `walk`/`stairs`/`ladder`/`climb`/`drop`/`gap` edges (`isOrdinarySegment`); it never plans a jump or a fall. The ground twin is the highest walkable floor under the stand-off spot more than 0.5" below the edge (a deck a container is stacked on), else the ground, and is skipped if a base there would overhang (`isBaseOverhanging`); the climb limit and drop thresholds use the real rise from that floor. Climb edges go from a drop spot's ground twin straight up to its over-air point on climbable pieces with a floor of 3" or less (cost: the vertical rise, plus the stand-off step in); climbing is ordinary movement, never difficult terrain (the old sheer-wall difficult/rush-stop logic is gone), and it is all-or-nothing: `settleEnd` leaves a model at the stand-off spot rather than part-way up. never chains two points over open air (short hops would add up to a jump), and a short (3" or less) ladder is only used going up (down it is a free drop). The A* heuristic is horizontal distance (drops cost horizontal only), the stairs get clearance waypoints round the wedge's footprint corners so a unit beside them can walk round to the foot, and `getDeckPoints` / the obstacle corners use `localToWorldXZ` (same convention as collision) so rotated pieces get correct points. The result is passed through `settleEnd`, which pulls the end back along the path (0.05" steps, never forward) so a move never stops suspended in mid-air, part-way up a ladder, or overlapping terrain or another model (`findEndOverlap`); when no ordinary route exists the fallback line is shortened to its ordinary prefix.
  - **`findJumpOption(state, unit, from, target)`** returns the jump or fall a model could declare from where it stands, or null: the model must be on a floor within `EDGE_SNAP_TOLERANCE` (0.5") of an edge it is heading out over (`isAtFloorEdgeToward`), the landing within 6" (horizontal), standable, and the single hop `[from, target]` unblocked. `jump-gap` for a level landing across 1-6" of air; `jump-drop` for a landing 3-6" below; `fall` (no dice) for a landing over 6" below. There is no path search.
  - **Host:** a move/rush/charge whose path contains a `jump-drop`, `jump-gap` or `fall` segment (or a chained run of gap over 1") must carry `payload.traversal = { kind, takeoff, landing }`; `validateDeclaredTraversal` recomputes the segment, kind, takeoff/landing match and the edge rule (`findJumpOption`) and rejects with "This move needs a jump: choose it explicitly" otherwise (also: only one jump per move, a declaration with no jump on the path is rejected, a squad declares per model, see below). Dice come from the existing `gap_jump` / `drop_jump` / `falling_defense` specs in `getDiceSpecs`, and the rolls are attached to the action's log entry as before.
  - **Squad jumps (batch 1D PR 15):** a squad move/rush carries `modelTraversals?: (DeclaredTraversal | null)[]` aligned with `modelPaths`. The host validates each model path with `validateDeclaredTraversal(state, unit, modelPath, modelTraversals[i])` (a path that needs a jump without a declaration is rejected as "Squad model N: ..."; more entries than models is rejected). `getDiceSpecs` appends, per jumping model in model order, that model's specs tagged `m<index>_` (`m1_gap_jump`, `m1_drop_jump`, `m1_falling_defense`; one hazard die); falling dice are only requested when every model of the squad could end up being the last survivor (jumpers >= living models), because otherwise a fall just removes the model. The summary `path` of a squad move only keeps its shared `hazard` roll when per-model jumps exist. Applying the move runs `applyModelPathTraversals`: each model path goes through `applyTraversalHazardsAndFalls` with that model and its own dice (prefix stripped by `diceForModel`); the events are logged as "Model N: ..." and all rolls stay on the log entry with their tags. A failed jump or fall destroys that model (`applyTraversalHazardsAndFalls` with a `model`: gap jump, failed drop jump and a drop over 6" alike) unless it is the last living model, and the activation ends once (`endActivationOnce`). **Later jumpers stop (batch 1I PR 31):** dice are still requested up front for every declared jumper (spec order and `m<index>_` tags unchanged), but `applyModelPathTraversals` tracks whether a declared jump has ended the activation (`terminated`); after that, each later declared jumper goes through `stopJumperAtTakeoff`: its model is placed at `DeclaredTraversal.takeoff`, its path and rolls are not resolved (the rolls stay on the log entry), its `modelMovementSpent` is cut back to the path up to the take-off spot, and a `jump-skipped` traversal event logs "Model N: jump not attempted (activation ended)". Walking models after a failure still finish. Used by squad moves, rushes and squad charge legs / charges.
  - **Group crossing, option C (14C-2 PR 4C):** `engine/crossing.ts` (replaces the PR 4B follow-the-leader router; `planFollowerCrossing` and the per-model reachability routing are gone). The leader declares the jump at its take-off edge (its own move must reach it) and the single roll is sized by its crossing. On a pass every other model may be *carried* across: the payload lists their living-model indices in `crossers`, each placed at its `modelPositions` entry on the far side within 1" (base edge) of a model already across (the leader's landing, another declared jumper's landing, or a carried model placed earlier, in any order). A carried model has no path to validate, spends no movement (its tally does not grow; hazards are not rolled for it) and is not part of the jump roll. `validateCrossers` (host, run before the squad coherency check so the reason is the crossing's) checks the leader declared a non-fall jump, Flying units are refused, a carried model declares no jump of its own, and every spot passes `crossingSpotProblem` (the same `endSpotProblem` as closest-approach: on the board, supported and not overhanging, no terrain or model overlap, more than 1" from other units except a charge's target, plus the far-side test `isBeyondCrossing` and no overlap with squad-mates) and then the reach (`withinCrossingReach`, fixed-point so chains work). The HUD uses the same functions: `crossingHover` (hover preview and click) -> `crossingPlacementProblem`; Auto placement is `autoPlaceCrossers` (models nearest the leader first; each tries its current spot shifted by the leader's own displacement, landing minus start, keeping the formation; otherwise the nearest legal spot within 1" of a model already across, searched on rings around the across models).   - **Squad follow-through (UX, owner 2026-11-10; no rule change):** in a squad's Advance, Rush or charge the player places one model (or a few) and presses Confirm; the models not yet placed follow. `engine/squadFollow.ts` `autoPlaceSquadFollowers(state, unit, { kind, models, placed, stopBeforeDifficult?, target? })` is pure. ### Engagement, the 1" rule and who strikes (per model, `engine/unitGeometry.ts`, `engine/spatial.ts`)
- **Contact:** `unitsInContact(a, b)` (any model pair within `ENGAGEMENT_EDGE_GAP` and `ENGAGEMENT_MAX_DY` = 1.5") drives `refreshEngagements`; `pointEngagesUnit(point, unit)` is the "would this end in melee contact" test for moves and rushes (host and HUD). Fight validation needs a pair within the gap and within `MELEE_MAX_VERTICAL_REACH`.
- **Charge reach:** `chargeContact(charger, target, anchorEnd, maxDy)` translates every charging model by the anchor's offset and asks for a pair within `CHARGE_END_EDGE_GAP` (returns `ok` / `too-far` / `too-high`); `chargeDestination(charger, target)` is the anchor spot that puts the closest charger model in base contact with the closest target model (the HUD plans the path to it).
- **1" keep-away (measured in 3D, owner decision 2026-11-10):** the gap between two models is `keepAwayGap3D(a, b)` = sqrt(horizontal base-edge gap^2 + dy^2), the edge gap floored at 0 once the bases overlap in plan view and `dy` the difference of the two models' foot heights. A model on a 3" deck is therefore never "within 1"" of one standing on the ground beneath it, as on the tabletop. `findMoveBlocker(state, unit, path, { keepAway: true })` refuses a path whose gap to any model of another unit drops under 1" (less `KEEP_AWAY_TOLERANCE`); a segment is sampled every 0.1" at the moving model's *actual* height (linear interpolation along a climb, stair or drop), not the segment's min/max, so a climb onto a deck is not held up by models standing under the landing. A model that starts closer than 1" (3D) is only stopped from getting closer than it began (`keepAwayLimitGap`). Physical overlap keeps its own check: bases within `UNIT_SEPARATION_DISTANCE` (1.0") centre to centre while less than `TIER_OVERLAP_DY` (1.8") apart in height. `ignoreUnitId` (the charge target) is exempt from the keep-away and the plain collision but is still never walked through (a path may not pass within 0.88" of one of its model centres at a similar height). The same helper decides every end-spot check: `findKeepAwayViolation` (used by `endSpotProblem` for closest-approach, pile-in and group-crossing placements, and by `settleEnd`), the Flying stop check, `deploymentFootprintProblem` (`keepAwayGapToUnit3D`) and `pushBackChargerModels`. The host applies it to move, rush (single and every squad model) and charge (toward everything but the target). `findNavPath({ keepAway: true })` routes with an octagon of waypoints round every model (horizontal, so it can only be over-cautious) and `settleEnd` pulls the end back with `findKeepAwayViolation`, so the preview already stops short; consolidation after melee does not use it. Melee engagement/reach (3" strike, 4" vertical limit) and the 3" cross-level coherency are separate rules and unchanged.
- **Keep-away zones (UI):** while a move, rush, declared charge (legs), squad model pick, group-crossing placement, push or pile-in is being planned, `GameHUD.keepAwayZonesForFlow()` builds a `KeepAwayZone[]` with `computeKeepAwayZones` (`client/src/ui/keepAwayZones.ts`): one disc per living model of every other unit within the mover's reach + radius + 4" margin, radius = their base radius + the mover's base radius + sqrt(1" - dy^2) with dy measured from the mover's starting height (`keepAwayCentreRadius`; = `KEEP_AWAY_CENTRE_DISTANCE` at equal height), the charge target / pile-in charger flagged `exempt`, models 1" or more above/below that height flagged `otherTier` (drawn faint at full radius: they do not block from there but can matter once the mover climbs or drops; the legend tooltip says so). It travels in `MarkerSnapshot.keepAwayZones` to `MarkerRenderer.setKeepAwayZones`, which rebuilds only when the list changes, and the HUD shows a one-line legend. It is a picture of the host rule only; nothing is decided from it. Consolidation does not use keep-away and shows no zones.
- **Flying chip and stop note (UI, owner request 2026-11-10; no rule change):** while a move, rush, declared charge leg or squad model pick is previewed, `GameHUD.showTraversalChip` adds to the hover note (`.sl-hud-move-warning`) a cyan "Flying · 4.2\" · over terrain" chip for a unit with `flying` (cost from `pathMovementCost` with the unit) and `MovePathMarker.flying` draws the line dashed cyan. When the planned path ends more than 0.25" (horizontally) short of the cursor, or below it by more than 0.5", `explainStop` (`client/src/ui/stopNote.ts`) names the cause in a fixed order: (1) the path spent the planner's allowance (`pathMovementCost` within 0.05" of the budget): "Stopped: out of movement", or "Stopped: difficult terrain caps the move at 6\"" when the Difficult Terrain cap set that budget; (2) a Rush held at the edge of difficult ground; (3) the 1" keep-away rule: the planner is run again with `keepAway` off, and the first sample along that route from the stop on that `findKeepAwayViolation` rejects names the unit ("Stopped: within 1\" of <unit name> (keep-away)"), which covers a stair whose head is within 1" of another unit; (4) otherwise a cursor higher than the end by more than 0.5" is "can't climb there (use stairs or a ladder)" and anything else "blocked by terrain". The note is also drawn at the stop point (`MovePathMarker.stop`). Presentation only: all causes come from engine functions, and the host validates the real action unchanged.
- **Who strikes:** `strikingModelCount(striker, foe)` counts the striker's living models within `MELEE_STRIKE_EDGE_GAP` (3", base edge) and `MELEE_STRIKE_MAX_DY` (4") of some foe model. `getDiceSpecs`, the charge/fight resolution and the strike-back all multiply attacks by it (at least 1). For a charge the count is taken after the charger moved in (`moveChargerModels`, or `placeSquadModels` for per-model squad charges) and the defenders have piled in (the defender's confirmed `pile-in-move`; a charge with nothing to pile in simulates the move on a copy of the state so the dice count matches).
- **Pile-in (batch 1I PR 33):** the defender places their own models. A final `charge` moves the chargers as before; if `pileInModelIds(target, charger)` (`engine/pileIn.ts`: living target models with no charging model within `CHARGE_END_EDGE_GAP` / 4" vertically; empty for a single living model) is not empty, the host sets `turnState.pendingReaction` of type `pile-in` for the target's owner (60 s, `data`: `chargeActionId`, `attackerId`, `targetId`, `weaponId`, `modelIds`, `maxDistance` 3, `chargeDistance`) and does **not** roll the strike. While it is pending only the defender's `pile-in-move` (or `respond-reaction`) is accepted. `pile-in-move { modelPositions, modelPaths? }` (living-model order) is checked by `validatePileIn`: only the listed models move; each path is ordinary movement (`pathMovementCost` <= 3", no gap jump, hazard or drop over 3"), clear under `findMoveBlocker` (keep-away waived toward the chargers), ends on a legal spot (`endSpotProblem`), and a model not touching a charger must end within 0.5" (base edge) of the `closestApproach` gap (budget 3", target = the charging unit, the others' submitted spots); the unit ends coherent, or no less coherent when it started incoherent. `getDiceSpecs` for `pile-in-move` returns the charger's strike dice counted from the submitted spots (`pileInStrikeSpecs`); applying it clears the reaction, places the models and runs `resolveChargeStrike` (the old inline charge strike: wounds, then the strike-back prompt, push-back or consolidation). The prompt's only option, `auto-pile-in` ("Auto place", the default), is a `respond-reaction` the host answers with `autoPileIn` (each listed model, nearest the chargers first, takes its `closestApproach` spot). The existing reaction timer in `GameManager` submits that default on expiry (and pauses while the peer is disconnected), so no client change was needed.
- **Pile-in HUD (batch 1I PR 34):** for a pending `pile-in`, `GameHUD.pileInContext()` is non-null only for the prompted (defending) player; it replaces the generic reaction prompt with a "Pile in" dock: the reaction countdown, one chip per listed model (`data.modelIds`; models already in contact are not chips and picking one on the board only toasts), **Auto place**, **Confirm** and **Reset** (the "Let the host place them" button was removed at the owner's request on 2026-11-09; the `auto-pile-in` choice remains for the timeout). Staging reuses the squad ideas without sharing the active-unit state: `pileInStaged` / `pileInPaths` (cleared when the reaction id changes), a click on the ground walks the selected model there, and a click on a charging model (or the charging unit) walks it into base contact with that model (toast and no move when the contact spot is beyond 3" or blocked), both with `findNavPath` (3" cap, keep-away, chargers exempt), overlap with a friendly or charging model is refused with a toast, and a coherency break only warns (it is enforced on Confirm). **Auto place** fills each unplaced listed model (nearest the chargers first) with `closestApproach` and keeps anything already placed; the player can then re-pick and move any model within 3". **Confirm** builds `pile-in-move` with every living model's position and path (unmoved models send a one-point path), runs `validateAction` locally and shows the host's refusal as a toast (for example "could get closer to the chargers"), otherwise submits. Markers: a 3" ring on the selected model (`movementRangePosition`), the hover or staged path, and the coherency ring set. The charging player sees "Waiting for <name> to pile in (Ns)" and no controls (the host is already refusing their actions). The old straight-line `consolidateSquadToward` pile-in was removed. A charge with nothing to pile in resolves in one step exactly as before, and `getDiceSpecs` for a charge that has to wait returns only the jump / hazard dice.

### Casualty picks (batch 1I PR 35, `engine/casualties.ts`)
Shooting, the charge strike, strike-back and `fight` apply wounds through `applyTrackedWounds`, which remembers each multi-model target as it was (`snapshotUnit`) and the wound applications on it (wounds, the pre-rolled wound-effect roll, fear bonus, Deadly step). Once the whole attack is resolved (so the log entry and its dice outcome are exactly as before), `deferCasualties` puts every surviving unit that lost models back to its snapshot and sets `turnState.pendingReaction` of type `pick-casualties` for the first such unit's owner (30 s, default option `auto-pick-casualties`). A unit the attack wiped out and a single-model unit never prompt. **Tabletop order (14C-3 Decision 3g):** `applyTrackedWounds` applies the wounds with `allocateWounds` and counts how often a wound had to start on an unhurt model (`unhurtStarts`) and how many unhurt models there were then (`unhurtAtFirstStart`); a unit prompts only when `unhurtStarts > 0` and at least two unhurt models could be chosen, also when no model died. `data`: `actionId`, `index`, `entry` (`unitId`, `count` = unhurt models to pick, in the order they take wounds, `lockedModelIds` = already-wounded models that take wounds first, `removed` = models the attack removes in total, `applications`), `rest` (entries for the other damaged units of the same action, in resolution order), `after` (the continuation: `shoot`, `fight`, `charge-strike`, `charge-resume` or `strike-back`, with attacker and target ids). Accepting replays the applications on the unit in the same order with the picks as the ordered list (`allocateWounds`; the reaction title is "Assign Wounds" when the unit's Tough is above 1, else the old "Remove Casualties"). `previewCasualtyPick(unit, entry, modelIds)` returns `{ modelId, wounds, destroyed }` for the locked models then the picks so far without touching the unit (for the HUD), then either prompts the next unit of `rest` or runs the continuation: `charge-strike` -> `settleChargeStrike` (consolidation / step back / the defender's strike-back prompt, whose dice are counted from the surviving models), `strike-back` -> `settleStrikeBack` (step back or consolidation), `fight` -> consolidation if the unit still died. The picks need no dice (`getDiceSpecs` returns null); the step-back, if any, is logged on the pick's own entry. **Deadly first (14C-3 PR 1D):** a shoot with several allocations and `resolveStrikes` / the Counter loop walk their weapons through `deadlyFirst` (a stable partition, Deadly weapons first) when applying wounds, so the ledger's `applications` (which the pick replays in order) already hold the Deadly wounds first. The timeout choice is answered with `autoPickCasualties(unit, entry)` (only unhurt models, `count` of them in order, starting from the squad without the locked models that die; each pick is the removal that leaves the smallest `coherencyShortfall`, ties by list order; a bare count still picks among all living models).

### Squad Targeting (per model, `engine/unitGeometry.ts`, `engine/squadTargeting.ts`)
`unit.position` is only an anchor (the centroid for squads). `livingModelPositions`, `closestModelPair` and `unitDistance` measure between the closest living models (base edge); `unitGap` (anchor to anchor) is no longer used by any rule. `firingModels(state, attacker, target, weapon)` runs `traceLineOfSight` from each attacker model's eye to each living target model and keeps the models that see one within range (same pair, base-edge gap; indirect skips sight). `validateAction` (shoot) requires at least one firing model per weapon allocation, `getDiceSpecs` and the resolution multiply the weapon's attacks by the number of firing models, and the `> 9"` rules read `unitDistance`. `unitBlockingSegment` skips the shooter's unit and the target's unit, so squad-mates never block while other units' models do. `targetCoverByMajority` judges each living target model with `findCoverSource` against its nearest firing model and gives cover only for a strict majority (a single-model target is judged alone). The HUD pre-checks call these same functions.

**Squad-mates and sight (14C-3 PR 1E).** Models of the shooting unit never block each other's sight, in every path: `firingModels`, `squadAim` (aim lines, "N of M" chip), the F9 debugger and the host's shoot validation all trace per model with the shooter's own unit id, which `unitBlockingSegment` skips (as it skips the target's id). `shared/tests/engine/squadMatesSight.test.ts` pins it with the starting triangle (front model with two behind, rear models directly behind and to the sides) and with a different unit in the way still blocking. The owner reported rear models of a squad treated as blocked by the front model. The engine paths could not reproduce it (see below); the likely cause was the aim-line colours: firing lines were deep orange (0xff7043) and blocked lines red (0xef5350), too close to tell apart, so a firing line through the front model read as blocked. Firing lines are now solid green (0x66bb6a) and blocked lines faint dashed red. The engine paths could not reproduce a block (a randomised sweep of squad positions on the Standard Battlefield found no case where a squad-mate changed who can fire), so the test is a regression guard. The attack-range sight fan (`computeLosVisibilityPolygon`) is a separate overlay: it skips the shooter's unit but lets *other* friendly units block at their anchor point, not per model.

**Which model carries which weapon (14C-3 PR 1E/1F, Decision 3d).** Models are numbered by their fixed place in `unit.models` (`modelNumber` in `client/src/ui/modelLoadout.ts`), so "Model 2" never shifts when others die. For a unit whose models do not all carry the same weapons (`loadoutsDiffer`, dead models included), or a multi-model unit with Tough above 1 (`showsModelHeadings`), the data card's weapons table is grouped by loadout (PR 1G, `modelWeaponGroups`): models carrying exactly the same weapons share one sub-heading row ("Model 1 / Model 2", ordered by lowest model number, members in number order, adjacent or not) followed by one set of weapon rows without carrier counts. Each model is its own `<span class="sl-hud-model-name" data-model-number>`; with Tough above 1 it also reads its wounds taken ("Model 2 · 2/3 W"), a removed model reads "Model N — removed" (greyed, still in its group; the group keeps its rows while any member is alive, and is greyed with no rows once all are removed). Hovering a model highlights only that model's name and its group's rows (the old header line is gone); the shoot preview draws one aim line per model labelled with every weapon it fires at the chosen target (all ranged weapons that reach it while aiming, only the assigned ones once weapons are assigned; `mergeAimLines`, drawn as `CSS2DObject` labels by `MarkerRenderer.setAimLines`); the casualty-pick buttons read "Model N (xW) · weapons". Squad placement chips, toasts and the dangerous-terrain casualty selector use the same fixed numbers. Units whose models all carry the same weapons keep the plain list, and the compact unit list on the left keeps counts ("2× Rifle").

### Shooting: two targets, Blast spread, Indirect
- **Targets:** a `shoot` names weapon allocations for at most two distinct target units; weapons with the same `name` must all use the same target (host rejects otherwise; the HUD moves same-name weapons together).
- **Blast(X):** `engine/blast.ts` `getBlastParticipants` lists the target, then every other enemy unit with a model within `BLAST_SPREAD_RANGE` (3", base edge) of any target model, nearest first. `countShotHits` gives the shot's hits (each becomes X, after all other rules) and `autoSplitBlastHits` / `autoSplitForParticipants` split them as evenly as possible (odd hit to the target first, then nearest units), capped at each unit's living models, re-spreading what a capped unit cannot take; hits above every cap are lost. Each unit resolves its slice (`resolveAttack`'s `BlastShare`: `offset`, `count`, `aimedAt`) with its own Defense and rules; cover is ignored for all. Hit modifiers (Stealth etc.) follow the aimed-at target. Neighbours' defense dice are extra specs in `getDiceSpecs`, purpose `blast_<unitId>_defense` / `_regeneration` (prefixed `alloc_<i>_` when the shot has several weapons), sized for the most hits that unit could take, since the split is only known once the to-hit dice are rolled. The log's dice outcome keeps the target's totals and lists neighbours in `blastSplash` (with their own `defenseRolls`); `blastSplits` records, per Blast weapon, the multiplier, the total hits, each unit's share and cap, and any lost hits, so the dice panel can print "Frag Launcher Blast(3): 1 hit × 3 = 3 hits → Squad A 2 · Squad B 1". Neighbour wounds go through the same casualty ledger and the wound baseline, so they count for end-of-activation morale.
- **Blast split prompt (14C-2 PR 10, Decision 34):** when a Blast weapon has more than one eligible unit and at least one hit lands, the host does not resolve the shot yet. `blastSplitPause` resolves it once on a throwaway copy (`resolveShoot` with a `prompts` list) to find the Blast weapons that need a split, leaves the real state untouched (no wounds, the shooter has not attacked) and sets `pendingReaction` of type `blast-split` for the target's owner. `engine/blastSplit.ts` holds the plain-data reaction (`BlastSplitData`: the shoot action, the server-rolled dice, and per Blast weapon the total hits, each unit's name and cap and the Auto split) and `validateBlastSplit`. A salvo with several Blast weapons gets one combined prompt with one row per weapon. The defender answers with a `blast-split` action (`splits: number[][]`, one count per eligible unit per weapon; the host validates whole numbers within each unit's cap that assign every hit that can land: any such split is fine, it need not be even) or `respond-reaction` with `auto-blast-split` (the host's own Auto split; also the timeout default). Either answer re-runs `resolveShoot` with the stored dice and the chosen split; the log entry of the answer carries the dice resolution (the shoot's own entry has none), then the usual casualty picks and end-of-activation flow follow. A lone eligible unit, or a shot that scores no hits, resolves at once with no prompt.
- **Indirect:** `ignoresSight(attacker, weapon)` is true for an Indirect weapon while the unit has not moved (`hasMoved` false, i.e. a Hold); `firingModels`/`squadAim` then skip line of sight and the shoot code skips cover from sight blockers. After moving it behaves like any weapon. The "-1 to hit after moving" penalty is removed.

### Cover Determination
- **In-Cover Status:** Targets with `in-cover` status always receive +1 Defense.
- **Low Cover Proximity Rule:** Intervening low cover (crates, low barricades) only grants +1 Defense if the line of fire crosses the piece and the defending target's base edge is within **1.0"** of it (`lowCoverEdgeGap`, measured base edge to piece; and the terrain is not adjacent to the shooter, i.e. `projDist > 1.0"`). Distant low crates in the middle of no-man's-land do not grant cover to targets standing in the open downrange, matching tabletop True-Line-of-Sight conventions.
- **Sight-Blocking Partial Cover:** For walls, jambs, sills and columns, the target's base edge must be within 1.0" of the solid and partially obscured (a torso-height flank ray is blocked while LoS stays open).

### Targeting Restrictions
- Must be in range
- Must have LOS (for shooting; ignored by `indirect` weapons while their unit holds)
- Engagement restrictions apply (engaged fighters typically fight rather than shoot)

### LoS & Cover Debugger (F9)
Pressing `F9` in-game activates the real-time spatial debugger:
- **Shooting Ray Trace:** Renders the 3D trajectory from shooter eye level (1.1" above its feet) to the target's eye/aim point, color-coded by obstruction (Cyan = clear LoS, Amber = passing through cover, Red = blocked LoS).
- **Boundary Intersections:** 3D disc rings highlight exact entry and exit coordinates where the shooting line breaches terrain bounding boxes.
- **Flank Rays:** Shows left and right torso-height rays (±0.3" from target center, 0.6" up) to verify partial obscuration by walls, jambs and sills.
- **Cover Map Wireframes:** Renders one wireframe per terrain solid and aperture (Cyan = solid LoS blockers, Amber = low cover, Green = firing-port apertures, Gold highlight = piece actively granting cover to target). An orange outline on the top face of a walkable floor marks a climbable piece (`isClimbable`: models can climb onto it without a ladder, rise up to 3"); the map editor shows the same outline on the selected piece.
- **HUD Analysis Card:** Displays real-time calculations: distance, Line of Sight status, cover reason, piece IDs, and coordinate breakdown of all intersected pieces.
- **Squads (per model):** for unit-vs-unit shooting `computeSquadShootingRayDebug` traces the detailed card (terrain crossings, flank rays) between the closest pair of models and adds `modelRays`: one eye-level ray per attacker model to its nearest visible in-range target model (cyan = that model fires, faint red = it cannot). The card tags read "N of M models fire" and "k/n target models in cover"; Line of Sight is clear while any model can fire and cover follows the more-than-half rule, not just the closest pair.

### Developer mode (lobby, 14C-1)
`F9` **while the lobby or main menu is showing** toggles developer mode (`client/src/ui/devMode.ts`, `Lobby`): a flag in `localStorage` (`skirmish_lab_dev_mode`), a short "Developer mode on/off" toast, and a "DEV" badge in the lobby corner. While it is on, the hidden playtest armies `test-army`, `test-squad-army`, `test-rules-army`, `test-jump-army` ("TEST: Jump Check": a plain 4-model squad, a Strider squad and a Flying squad, speed 6") and `test-scout-ambush-army` ("TEST: Scout & Ambush Check": two ordinary squads (Test Guard carries Repel Ambushers and Hold the Line), two Scout squads and two Ambush squads, for checking setup) appear in both army pickers. While off (the default) they are hidden, and a TEST army that was selected falls back to the default army (also when the lobby hands the choice to the game). The Lobby's F9 listener ignores the key whenever the lobby is hidden, so in-game `F9` still opens only the LoS debugger above and never touches the flag.

### Move preview: jumps and too-wide gaps
The hover preview treats squad models like single models: a model standing at a floor edge is previewed with its declared jump (dashed red hop, floating label, chip) before the click (`resolveMoveTarget` is called with `allowJump` for every unit). When the cursor is across open air from the edge and the hop (take-off to landing, straight line) is over 6", `findTooWideGap` (`traversal.ts`) returns the distance and the chip reads "Too far to jump (N\", max 6\")"; no jump is offered and the host check is unchanged. The hint is skipped when ordinary movement still reaches the cursor another way.

### Shooting preview (aim lines)
While choosing a shooting target (and while confirming a shot), `squadAim` (`squadTargeting.ts`) gives the HUD one aim per living attacker model: the target model the player pointed at when that model sees it in range, else its nearest visible, in-range target model (or the nearest model when none is visible, drawn as a faint dashed red line; lines for models that fire are solid green). Preview only: who fires, attacks and cover do not depend on the clicked model. `MarkerRenderer.setAimLines` draws those lines at eye height and a yellow ring under the target model the cursor is on when at least one firing model can see it. A chip above the hint reads "N of M models can fire" for squad shooters. The weapon used is the selected weapon chip, else the first ranged weapon that can fire. Single-model shooters get one line and no chip. The engine does all the range and sight tests; the HUD only draws.

## Game State Transitions

### State Machine
```typescript
class GameStateMachine {
  // Host-only
  validate(action: GameAction): ValidationResult;
  apply(state: GameState, action: GameAction): GameState;
  canTransition(from: GamePhase, action: ActionType): boolean;
}
```

### Applying Actions
When host applies a valid action:
1. Clone current state (immutable updates)
2. Apply action changes
3. Add to action log
4. Update activation state if needed
5. Check win conditions
6. Return new state

## Win Conditions
Victory conditions are mission data. v1 ships a simple elimination mission; objective-based missions come later as data packs.

### Concede and the results screen (HUD, 14A)
- The header carries a muted **Concede** button for both players until the match is over (deployment included). It opens a confirmation ("Concede the match? You lose and your opponent wins."); only the confirmed button sends a `concede` action. While waiting it reads "Conceding…" and is disabled.
- A guest that gets no confirmed state within 5 s gets the button back and a toast ("Couldn't reach your opponent; the concede wasn't sent."); nothing is applied locally. The host applies its own concede locally, so it never times out. A rejection also restores the button.
- `GameManager` queues a `concede` that arrives while another action's dice request is in flight and applies it right after that action; if that action already ended the game, the queued concede is dropped silently.
- The conceder stays on the game-over modal ("Defeat", "<name> conceded") and the opponent sees "Victory". Conceding never calls `onReturnToLobby`.
- The modal is built from `summarizeMatch(state)`: title (Victory / Defeat / Draw), the reason, "Rounds played: N of 4", the objective score and per-objective breakdown, one loss line per side ("<Name> lost U of T units (M of N models)", host first), and the Return to Lobby button in an actions row with room for a second button.
- After game over the "Opponent disconnected" banner is suppressed (leaving through Return to Lobby is expected); a disconnected peer shows "<name> has left." on the modal instead.

### Rematch flow (HUD and storage, 14B)
- The modal's actions row has **Play Again** next to Return to Lobby, for both players after every ending. Pressing it sends one `request-rematch` and the button reads "Waiting for <opponent>…" (disabled). The opponent sees "<name> wants a rematch" and a primary **Accept rematch**. If the opponent has left (the "has left." line), the button is disabled and reads "Opponent has left".
- When both have asked, the host's `applyAction` returns the fresh starting state (new `gameId`). On a different `gameId`, `GameHUD.syncFromState` clears all per-match local state (flow, staged squad placements, casualty and pile-in picks, concede state, last-round and log tracking, toast) and shows "Rematch started — same armies, same map"; `GameView.syncFromState` clears markers and outcome tokens. The camera keeps its role view.
- Storage: game over clears the room snapshot and the active session. When a non-game-over state with a different `gameId` follows a game-over snapshot, `GameManager` resets its in-memory snapshot history to the new match, resumes saving snapshots, and calls the `onSessionResume` hook; `main.ts` uses it to write the same active-session record as `onPeerReady`, so a reload during the rematch resumes the rematch.

## Balance & Validation
- Host enforces all rules strictly
- No client-side shortcuts
- All random elements go through the server
- Action history preserved for debugging

## Implementation Notes

### Data-Driven Design
- Fighter/weapon/special-rule definitions are data files (JSON/TS)
- Rules are implemented as pure functions
- Ruleset differences (Firefight vs future packs) are data, not code

### Testing Considerations
- Pure functions are easy to test
- Game state transitions are deterministic given the same inputs and dice results
- Dice results come from the server but resolution logic is deterministic

### Performance
- Keep validation fast
- State copies are efficient enough for turn-based play
- Action log grows over game length but remains reasonable
